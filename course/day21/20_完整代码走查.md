## 1. tools/tool_registry.py

### ToolDefinition

```python
@dataclass
class ToolDefinition:
    name: str
    description: str
    parameters: dict[str, Any]
    handler: ToolHandler

    def schema_summary(self) -> str:
        props = self.parameters.get("properties", {})
        keys = ", ".join(props) if props else "无"
        return f"{self.name}({keys}) — {self.description}"
```

**要点**：parameters 为 JSON Schema 子集；handler 必须返回 str。

### ToolRegistry

- `register` — 空名 `ValueError`  
- `get` / `list_tools` / `list_names`  
- `schemas_for_prompt` — 多行文本，供未来 system prompt

## 2. tools/executor.py

### execute

```python
tool = self.registry.get(name)
if not tool:
    return ToolResult(..., error=f"未知工具: {name}")
try:
    output = _invoke(tool, args)
    return ToolResult(..., success=True, output=output)
except TypeError as exc:
    return ToolResult(..., error=f"参数错误: {exc}")
```

### _invoke

- 按 `properties` 键过滤 args  
- `required` 缺失时 query/text 互补

if cmd == "/tool":
    if not self.tool_executor:
        return True, "工具调用未启用。请传入 tool_registry。", False

        return True, self.tool_executor.list_help(), False

## 10. tool_registry.py 逐段中文讲解

### 10.1 ToolHandler 类型别名

`ToolHandler = Callable[..., str]` 表明所有工具处理函数必须返回字符串。这是智链科技工具层的**硬约束**：无论内部逻辑多复杂，最终都要落成可嵌入对话或日志的文本。林晓在走查时尝试让 handler 返回 dict，被陈默在 code review 中退回。

### 10.2 ToolResult.summary 格式

成功时 `[{name}] {output}`，失败时 `[{name}] 失败: {error}`。此格式与 `/tool` 命令输出、test 断言、运营 SOP 三方对齐。修改 summary 格式属于**破坏性变更**，需同步改 test_sprint3 与课件。

### 10.3 register 空名校验

`if not tool.name: raise ValueError` 防止无名工具覆盖字典键。看似琐碎，实则是注册表不变式。周航曾建议用 name 作 UUID，被否决——工具名是人类可读的 API。

### 10.4 faq_lookup 闭包

闭包捕获 `faq_matcher` 实例。若 matcher 内部阈值在运行时被修改，handler 行为随之变化，无需重新 register。这是**引用语义**的好处。

### 10.5 rag_search 的 top_k

handler 签名 `rag_search(query: str, top_k: int = 3)`。JSON 调用可省略 top_k；`_invoke` 不传时 Python 默认生效。简写 `/tool rag_search 年化收益` 只有 query 键，top_k 走默认 3。

### 10.6 intent_classify 与 classify().summary()

不返回原始 IntentResult 对象，而是 summary 字符串，减少工具层对 prompts 内部类型的泄漏。若需 JSON，可在 handler 内 json.dumps，但当前规范是 human-readable。

### 10.7 parse_tool_arguments 设计意图

降低运营使用门槛：大多数调试只需 `/tool faq_lookup 自然语言问题`，不必手写 JSON。同时保留 JSON 路径供自动化脚本精确传 top_k 等参数。

## 11. executor.py 逐段中文讲解

### 11.1 为何捕获 TypeError 与 Exception 分开

TypeError 几乎总是参数名/缺参问题，消息可直接给调试者。其他 Exception 兜底防止单个工具 bug 搞挂 REPL。生产环境可在此加 logger.exception。

### 11.2 _invoke 的 query/text 互用

历史原因：部分工具要 query，部分要 text，简写参数同时填充两个键。_invoke 在 required 缺省时交叉补全。这是**兼容性设计**，非理想 API，但减少课件与演示摩擦。

### 11.3 list_help 与 schemas_for_prompt 区别

前者给 `/tool list` 人类阅读；后者给 LLM system prompt，行首有「可用工具：」总标题。内容来源都是 `list_tools()`，单源维护。

## 12. orchestrator.py 逐段中文讲解

### 12.1 为何 assistant 必填

编排器是 ChatAssistant 的**外包装**，不是替代。messages 历史、LLMClient、auto_route 实现仍在 assistant 内。orchestrator 若重写 chat 逻辑会导致 Day 14–20 投资浪费。

### 12.2 自动 build_nexus_tools

当 `tool_registry is None` 时，用传入的 faq_matcher、rag_service 等自动构建。方便测试只关心 FAQ 直答而暂不关心自定义工具的场景。integrated_assistant_demo 则显式传入 tools，演示完整四工具。

### 12.3 enable_auto_route 副作用

每次 handle_message 强制 `assistant.auto_route = True`。意味着即使用户构造 assistant 时设 False，经编排器后仍走路由。产品决策：经编排器的消息**默认**要智能路由。

### 12.4 run_tool 与 handle_message 分离

run_tool 不修改 messages，不触发 FAQ 直答策略。适合 API `POST /tools/execute` 调试端点。handle_message 是对话主路径。

## 13. cli_assistant.py /tool 分支讲解

### 13.1 tool_executor 来源

`ChatAssistant.__init__` 接收 `tool_registry`，内部 `self.tool_executor = ToolExecutor(tool_registry) if tool_registry else None`。因此传 registry 即启用 /tool。

### 13.2 split(maxsplit=1)

`parts = arg.split(maxsplit=1)` 保证 JSON 参数中的空格不被拆开。`/tool rag_search {"query":"a b"}` 正确。

### 13.3 命令不进入 messages

handle_command 返回 `(handled, msg, continue_chat)`，/tool 通常 continue_chat=False，历史不追加工具输出为 user 消息——避免污染 LLM 上下文。FAQ 直答同理。
