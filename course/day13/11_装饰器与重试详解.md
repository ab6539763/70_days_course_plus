## 一、装饰器在 NexusAgent 中的战略位置

Day 12 的 `LLMClient.complete` 是**单次尝试**的纯函数式调用链。生产环境面临：

- 云 API **限流**（429）  
- 网关 **瞬时 5xx**  
- 网络 **抖动**与**长尾延迟**

陈默在 Sprint 2 评审中划定：**横切关注点用装饰器**，不污染 `client.py` 传输逻辑。

```
业务调用方 → ResilientLLMClient.complete → [@retry [@with_timeout 裸 complete]]
```

## 二、装饰器机制详解

### 2.1 闭包与三层工厂

`retry(max_attempts=3)` 的执行时序：

1. `retry(3)` 被求值 → 返回 `decorator` 函数  
2. `decorator(func)` 被调用 → 返回 `wrapper`  
3. 用户调用 `wrapper(*args)` → 循环尝试 `func(*args)`

与 `decorator_demos.repeat(3)` 同构，培养**统一心智模型**。

### 2.2 functools.wraps 的必要性

```python
@functools.wraps(func)
def wrapper(*args, **kwargs):
    ...
```

复制属性：`__name__`, `__doc__`, `__annotations__`, `__module__`。

单元测试中 `patch.object(client, 'complete')` 依赖正确名称；调试器栈显示 `_call` 而非 `wrapper` 层叠混淆。

### 2.3 带参 vs 无参

| 类型 | 示例 | 第一层接收 |
|------|------|------------|
| 无参 | `@log_call` | 被装饰函数 |
| 带参 | `@retry(3)` | 装饰器参数 |

## 三、retry 实现剖析

### 3.1 控制流

```python
for attempt in range(1, max_attempts + 1):
    try:
        return func(*args, **kwargs)
    except BaseException as exc:
        last_exc = exc
        if attempt >= max_attempts or not predicate(exc):
            raise
        sleep_for = min(delay, max_delay)
        ...
```

**设计抉择**：

- 最后一次失败 **re-raise 原异常**，保留 `__cause__` 链  
- `predicate` 可注入，默认 `is_retryable_error`  
- `on_retry` 钩子供日志/指标，不强制

### 3.2 指数退避

避免「惊群」：全体客户端在同一秒重试再次打爆 API。

默认：1s → 2s →（若还有）4s… capped at 30s。

企业扩展：加 **full jitter** `sleep = random.uniform(0, sleep_for)`。

### 3.3 is_retryable_error 哲学

```python
DEFAULT_RETRYABLE_STATUS = frozenset({429, 500, 502, 503, 504})
```

| 类别 | 策略 | 理由 |
|------|------|------|
| 客户端 4xx（除429） | 不重试 | 请求本身有误 |
| 429 | 重试 | 显式限流，等一等 |
| 5xx | 重试 | 服务端瞬时 |
| 无 status_code | 重试 | 网络/超时类 |

`ConfigError` / `ModelValidationError`：**配置与校验**，重试零收益。

## 四、with_timeout 与 urllib

### 4.1 线程池包装

同步 `urllib.request.urlopen` 无 asyncio 取消语义。`ThreadPoolExecutor` + `future.result(timeout)` 是跨平台 MVP。

### 4.2 与 urllib 自带 timeout 关系

`default_transport` 内已有 `urlopen(..., timeout=60)`。双层超时：

- urllib：单次 socket 读  
- `with_timeout`：整个 `complete`（含 body 构建、解析）

外层 `RetryPolicy.timeout_seconds` 默认 60，与传输层对齐。

### 4.3 超时异常可重试性

超时 → `APIError` 无 code → 可重试。合理：偶发长尾；若持续超时，attempt 用尽后失败。

## 五、ResilientLLMClient 集成

### 5.1 为何在 __init__ 构建装饰函数

```python
self._complete_resilient = self._build_resilient_complete()
```

- 装饰开销只发生一次  
- `policy` 固化进闭包  
- `complete` 方法体保持一行转发

### 5.2 继承而非组合

子类继承 `LLMClient`，对外仍 `isinstance(x, LLMClient)`。Day 14 `cli_assistant` 可类型注解 `LLMClient` 接受弹性实现。

### 5.3 on_retry_log

```python
print(f"  ⏳ 重试 {attempt}/{self.policy.max_attempts - 1}: ...")
```

分母 `max_attempts - 1` 表示「最多重试次数」，人性化文案。

## 七、反模式清单

1. **对所有 Exception 无差别重试** — 掩盖编程错误  
2. **无限重试** — 必须 `max_attempts` 上限  
3. **固定间隔重试** — 易同步撞车  
4. **重试 401** — 浪费配额  
5. **超时装饰器包在 retry 外** — 阻断重试
